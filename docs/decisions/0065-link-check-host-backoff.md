# 0065. リンクチェックで kyoiku-press.com だけレート制限を掛ける

- 状態: 採用
- 日付: 2026-08-19
- 関連 issue: #511
- 関連 ADR: 0055（kknews.co.jp の除外）、0056（MEXT 採用公告の除外）
- 関連 PR: `fix/link-check-concurrency`

## 背景

週次の自動リンクチェック（lychee、`.github/workflows/link-check.yml`）が 2026-08-10 に立てた #511 は、`kyoiku-press.com`（日本教育新聞）の 4 URL を 502 Bad Gateway として報告した。調査の結果、これは偽陽性と確定した。

- 報告された 4 URL は、2026-08-19 に逐次 curl で全数 200 を返した。`<title>` も各記事のままで、記事が消えたわけではない。
- 同日に link-check を手動実行すると、また 502 が 5 本出た。ただし 8/10 の 4 本とは 1 本も重ならない。その 5 本も逐次アクセスでは 200 だった。
- lychee の既定 User-Agent（`lychee/0.24.2`）でも 200 が返る。UA によるブロックではない。
- `kyoiku-press.com` は lychee がチェックしているドメインの中で最も多く、ユニーク 305 本（`src/data/articles/*.json` の `sourceUrl`）。リポ全体では `kknews.co.jp` の 429 本が最多だが、こちらは ADR 0055 で除外済みで実際には叩いていない。

特定の URL が壊れているのではなく、1 つの WordPress サイトに短時間で集中してリクエストを送り、相手が数本を取りこぼしていた。lychee の既定はホストあたり同時 10・最小間隔 50ms で、305 本をこの速度で叩いていた。

放置できない理由がもう一つある。この workflow は「open な link-check Issue があれば新しい Issue を作らない」実装なので、偽陽性の Issue が開いている間は**新しいリンク切れが人に通知されない**（lychee 自体は走り続け、レポートはアーティファクトに残る）。#105 / #204 / #256（ADR 0055）と同じ構図で、ノイズが通知経路を塞ぐ。

## 検討した選択肢

- **A) 毎回手動でクローズする**（現状）。上記のとおり、開いている間は通知が止まる。
- **B) 502 を `--accept` に追加する**。1 行で済むが、全ホストで本物の 502 を見落とす。
- **C) `kyoiku-press.com` を `--exclude` する**（ADR 0055 と同じ手）。確実に静かになるが、305 本の一次出典が監視対象から外れる。kknews は CI から到達できず実カバレッジがゼロだったため失うものが無かったのに対し、こちらは到達できている。
- **D) `--host-concurrency` / `--host-request-interval` で全ホストのレートを落とす**。相手への負荷は下がるが、**応答が返らないホストが 1 つ出たときに全体を道連れにする**。同時 1 に落とすと、そのホストの URL がすべて直列にタイムアウト待ちになる。ADR 0055 の kknews は「CI から全 URL がタイムアウト」が実際に起きた事例で、仮定の話ではない。job がタイムアウトでキャンセルされると `Create Issue on broken links` は（`if: always()` ではないため）走らず、リンク切れが検出も通知もされないまま終わる。
- **E) `lychee.toml` の `hosts` で当該ホストだけレートを落とす**。影響が 1 ホストに閉じる。

## 決定

E を採用する。リポジトリ直下に `lychee.toml` を置き、`kyoiku-press.com` だけ同時 1・最小間隔 1 秒にする。ワークフローの args は元のまま（`--host-*` は使わない）。

lychee は `--config` の既定値が `lychee.toml` なので、ファイルを置くだけで読まれる。チェックの条件（`--accept` / `--exclude` / `--timeout`）は従来どおり args に残し、設定ファイルにはホスト別のレート制限だけを書く。

値は実測で決めた。同じ `dist`（Total 24072 / Unique 1929 が 3 回とも一致）、同じ lychee v0.24.2、2026-08-19:

| 設定 | 502（ユニーク URL） | lychee ステップ | job 全体 | run |
| --- | --- | --- | --- | --- |
| 既定（同時 10 / 50ms） | 5 | 47s | 1m25s | 32216874809 |
| 全ホスト 同時 1 / 1s | 0 | 5m22s | 5m52s | 32220157304 |
| **`lychee.toml` で 1 ホストのみ 同時 1 / 1s** | **0** | **5m8s** | **5m34s** | **32220986945** |

3 本ともキャッシュ無しで全 URL を引いている。1 本目は 2 日前のキャッシュを復元したが lychee が `Cache is too old` として破棄し、2・3 本目は `restore-keys` を一時的に外して `Cache not found` を確認した。

所要時間が既定の 47 秒から 5 分台に伸びること自体が、当該ホストが 1 秒に 1 本へ絞られている裏づけになる（305 本 × 1 秒 ≈ 305 秒が律速）。全ホストに掛けた場合との差が 14 秒しかないのは、他ホストが並行して処理されるため。

**緩めると 502 が消えることは、原因が負荷であることと整合する。** IP で弾かれているなら間隔を空けても答えは変わらないので、kknews で確認された機序（データセンター IP のブロック）ではない。ただし各条件 n=1 で、対象は「毎回違う数本が落ちる」サーバなので、これは矛盾しないという以上の主張はしない。

## 影響

- 週次実行が 47 秒から 5 分台に伸びる（job 全体で 5m34s）。週 1 回のジョブなので許容する。
- 実行窓が広がるぶん、`cancel-in-progress: true` により、実行中に `workflow_dispatch` を打つと週次 run がキャンセルされる可能性も広がる。実害は小さい。
- 検知能力は落ちない。`--accept` や `--exclude` と違い、全 URL を従来どおりチェックする。
- **本 PR をマージしただけでは通知は再開しない。** #511 を close して初めて、次回以降のリンク切れが Issue として立つ。
- 再評価の条件: この設定でも 502 が再発する場合は、負荷以外の原因（相手側の恒常的な不調・IP ベースの制限への移行）を疑い、B か C を検討する。他のドメインで同じ偽陽性が出たら `lychee.toml` にホストを追加する。

## 補足: lychee のキャッシュについて

`--cache-exclude-status` は未指定だが、lychee 0.24.2 が `.lycheecache` に書くのは `--accept` に含まれるステータスだけで、502 や 404 は書かれない。したがって「前回の失敗が再実行で再現する」ことはない。

注意すべきは逆で、**成功はキャッシュされるため、同じ日に手動で回し直すと前回 200 だった URL は引き直されない**。今回の測定で `restore-keys` を一時的に外したのはこのためで、外さないまま測ると「毎回違う数本が落ちる」母集団を過小にサンプルしてしまう。修正の効果を手動実行で確かめるときは、キャッシュを復元しない状態で回すこと。

# 0065. リンクチェックでホスト単位の同時接続と間隔を緩める

- 状態: 採用
- 日付: 2026-08-19
- 関連 issue: #511
- 関連 PR: `fix/link-check-concurrency`

## 背景

週次の自動リンクチェック（lychee、`.github/workflows/link-check.yml`）が 2026-08-10 に立てた #511 は、`kyoiku-press.com`（日本教育新聞）の 4 URL を 502 Bad Gateway として報告した。調査の結果、これは偽陽性と確定した。

- 報告された 4 URL は、2026-08-19 に逐次 curl で全数 200 を返した。`<title>` も各記事のままで、記事が消えたわけではない。
- 同日に link-check を手動実行すると、**また 502 が 5 本出た。ただし 8/10 の 4 本とは 1 本も重ならない。** その 5 本も逐次アクセスでは 200 だった。
- lychee の既定 User-Agent（`lychee/0.24.2`）でも 200 が返る。ADR 0055 の kknews と違い UA ブロックでもない。
- `kyoiku-press.com` はこのリポで最も多く引用しているドメインで、ユニーク 305 本（`src/data/articles/*.json`）。他のどのドメインより多い。

つまり特定の URL が壊れているのではなく、**1 つの WordPress サイトに短時間で集中してリクエストを送り、相手が数本を取りこぼしている**。lychee の既定はホストあたり同時 10・最小間隔 50ms で、305 本をこの速度で叩いていた。

放置できない理由がもう一つある。この workflow は「open な link-check Issue があれば新しい Issue を作らない」実装なので、**偽陽性の Issue が開いている間、他の本物のリンク切れは一切検出されない**。#105 / #204 / #256（ADR 0055）と同じ構図で、ノイズが検知能力そのものを止める。

## 検討した選択肢

- **A) 毎回手動でクローズする**（現状）。上記のとおり、開いている間は検知が止まる。
- **B) 502 を `--accept` に追加する**。1 行で済むが、全ホストで本物の 502（サーバー障害でページが出せない状態）を見落とす。403/429/503 の許容とは意味が違い、502 は「上流が落ちている」を含む。
- **C) `kyoiku-press.com` を `--exclude` する**（ADR 0055 と同じ手）。確実に静かになるが、305 本の一次出典が監視対象から外れる。kknews と違いこちらは CI から到達できている＝実カバレッジがあるので、失うものが大きい。
- **D) ホスト単位の同時接続と間隔を緩める**（`--host-concurrency` / `--host-request-interval`）。相手への負荷を下げる方向で、検知能力は落とさない。

## 決定

D を採用し、`--host-concurrency 1` と `--host-request-interval 1s` を lychee args に追加する。

値は推測ではなく実測で決めた。同じ `dist`、同じ lychee v0.24.2、2026-08-19 の 3 回の実行:

| 設定 | 502（ユニーク URL） | lychee ステップ所要 |
| --- | --- | --- |
| 既定（10 並列 / 50ms） | 5 | 47s |
| 4 並列 / 200ms | 3 | 1m11s |
| **1 並列 / 1s** | **0** | **2m36s** |

段階的に緩めると 502 が単調に減り、1 並列 1 秒で完全に消えた。これは「相手を叩きすぎている」という診断を支持し、同時に「datacenter IP を弾かれている」（kknews で確認された機序）を否定する — IP で弾かれているなら、間隔を空けても返る答えは変わらない。

## 影響

- **週次実行が 47 秒から 2 分半に伸びる**（job 全体で 4 分弱）。週 1 回のジョブなので許容する。
- **設定は全ホストに適用される。** lychee はホスト別の設定を `lychee.toml` の `hosts` でしか受け付けず、args だけで完結している現行の運用を崩す方が高くつくと判断した。将来ホスト別に分けたくなったら設定ファイルの導入を再検討する。
- **検知能力は落ちない。** `--accept` や `--exclude` と違い、全 URL を従来どおりチェックする。本物のリンク切れは引き続き検出される。
- 他の引用先にも同じ緩和がかかるため、ボット対策の緩いサイトでの偶発的な失敗も減ることが期待できる（副次的効果であり、測定はしていない）。
- **再評価の条件**: この設定でも 502 が再発する場合は、負荷以外の原因（相手側の恒常的な不調・IP ベースの制限への移行）を疑い、B か C を検討する。

## 補足: キャッシュについて

3 回の実行はいずれも直前の run の lychee キャッシュを復元している（`restore-keys: lychee-`）が、所要時間は設定に比例して 47s → 1m11s → 2m36s と伸びた。キャッシュが効いていれば短縮されるはずで、実際にはほぼ全 URL を毎回チェックしている。上表の比較が同条件どうしであることの裏づけとして記録しておく（なぜ効いていないかは追っていない）。

なお `--cache-exclude-status` は未指定なので、原理上は失敗もキャッシュされうる。週次実行は `--max-cache-age 1d` を超えて間隔が空くため実害はないが、**同じ日に手動で回して結果を確かめる運用では、前の実行の失敗が再現しうる**点に注意する。

# 0065. bot PR の滞留を検知する。監視の起点はラベルに置き、全 job に timeout を宣言する

- 状態: 採用
- 日付: 2026-08-19
- 関連 ADR: [`ADR 0022`](0022-recheck-nikkyo-membership.md)(週次 paywall 再判定) / [`ADR 0042`](0042-fetch-news-token-elevation.md)(fetch-news の PAT 昇格) / [`ADR 0020`](0020-persistent-article-denylist.md)(削除記事 ID の永続追跡。週次ヘルスチェックはその §残タスク)
- 関連 PR: 本 ADR の実装

## 背景

2026-08-17 21:26 UTC、ADR 0022 の週次再判定が PR #539 を立て、auto-merge を armed にして**成功で終了した**。その後 PR 側の Playwright E2E が `npx playwright install-deps chromium` で apt ミラーに到達できず無限リトライに入り、**6h0m15s でジョブ既定タイムアウトに当たって cancel** された。PR はマージされないまま **29.4 時間** open で残り、運営者が偶然気づくまで誰にも通知されなかった。

ここに独立した 2 つの欠落がある。

### 欠落 1: ジョブに timeout が無く、ハングの代償が 6 時間

`timeout-minutes` を宣言していない workflow が 7 本あった(`audit` / `cf-purge` / `checks` / `dependabot-auto-merge` / `e2e` / `link-check` / `vrt`)。GitHub の既定は 360 分なので、ネットワーク由来の停止はすべて 6 時間ぶん Actions 時間を焼いてから赤くなる。テストは 1 件も走っていない。

同じ経路は VRT にもある。`vrt.yml` は Playwright をキャッシュせず毎回 `install --with-deps` するため、同じ apt に依存している。

### 欠落 2: bot PR が「作られたあと」に失敗しても誰も見ていない

`fetch-news.yml` と `recheck-nikkyo-membership.yml` は、PR を作って auto-merge を armed にした時点で成功する。その後に required check が落ちても、**workflow 自身は緑のまま**なので失敗通知が出ない。ADR 0020 の health-check は自分自身の schedule 失敗しか拾わず、PR の滞留は守備範囲外だった。

実測(2026-08-19)でこれは単発の事故ではない。

| ラベル | 全件 | 2 時間を超えた滞留 |
| --- | ---: | --- |
| `auto-collect` | 189 | 4 件(#127 2.3h / #138 10.6h / #142 12.3h / #374 18.2h) |
| `recheck-membership` | 13 | 2 件(#167 8.5h / #539 29.4h) |

この 6 件を除いた健全側は、`auto-collect` 153 件が最大 3.6 分、`recheck-membership` 11 件が最大 1.4 分でマージされている。**正常と異常は 2 桁以上離れており、時間による判定が成立する。**

## 検討した選択肢

### A. 滞留した bot PR を定期的に探して Issue にする(採用)

PR は「作られた事実」より「マージされない状態が続いていること」で異常が分かる。定期的に open な bot PR の経過時間を見れば、原因が CI 失敗でも check の保留でもコンフリクトでも同じ 1 つの装置で拾える。

### B. bot workflow 側で auto-merge の成立まで待つ(却下)

`fetch-news` は 1 日 2 回動く。CI 完了まで待たせると、その間ジョブが占有され、待ち時間そのものが timeout の対象になる。失敗の検知を、失敗しうる同じジョブの内側に置くことになる。

### C. `workflow_run` で e2e / checks の失敗を監視する(却下)

拾えるのは「check が赤くなった」場合だけで、**pending のまま止まった場合を拾えない**。#539 は 6 時間 in-progress のままだった。またすべての PR が対象になるので、人間の PR の失敗まで Issue 化してしまう。

### D. GitHub 標準の失敗通知に任せる(却下)

#539 では E2E の cancel 時に通知は出ていたはずだが、実際には 29.4 時間気づかれなかった。通知は届いても「PR がマージされていない」という状態は表現しない。

## 決定

A を採用する。

### D1. 監視の起点はラベルに置く

対象は PR の作者ではなくラベル(`auto-collect` / `recheck-membership`)で選ぶ。

ADR 0042 で fetch-news のトークンを PAT に昇格させた結果、**bot が立てた PR の author は運営者本人と区別できない**。作者による絞り込みは原理的に不可能で、ラベルが唯一の識別子になる。

### D2. 閾値は 2 時間、cron は 6 時間ごと

健全側の最大が 3.6 分なので、2 時間は約 33 倍のマージンがある。過去の滞留 6 件はすべて 2 時間を超えており、いずれも真陽性として拾える。

**「8 時間以内に検知できる」とは書かない。** GitHub の schedule は定刻に発火しない。本リポの固定時刻 cron 全 263 実行の実測で、遅延は中央値 78 分・p90 223 分・最大 351 分(5.8 時間)だった。したがって検知の外縁は 6 時間(cron 間隔) + 2 時間(閾値) + 5.8 時間(遅延) ≈ **14 時間**と見るべきで、8 時間は典型値であって保証ではない。

### D3. Issue は PR 1 本につき 1 本、タイトルに PR 番号を含める

タイトルを `bot-pr-watchdog: PR #<N> が滞留しています` に固定し、同じタイトルの open Issue があれば何もしない。6 時間ごとに走ってもコメントが積み上がらない。

重複判定は **open Issue の完全一致タイトル**で行い、`gh issue list --search ... in:title` は使わない。GitHub の検索インデックスは反映が遅れることがあり、連続実行で同じ Issue を二重に立てうる。

### D4. 壊れたときに緑で終わらせない

この種の装置は、壊れても「異常なし」と見分けがつかない形で失敗する。次の 3 つを明示的に落とす。

1. **ラベルの分岐**: bot workflow の `--label` を実体から抽出し、監視対象と食い違えば `exit 1`。存在確認だけでは、bot が別のラベルを使い始めて古いラベルがリポジトリに残っている場合を検知できない。抽出対象のファイルは列挙せず「PR を作る workflow」から導出するので、3 本目が増えても気づく。
2. **ラベルの消滅**: 監視対象のラベルがリポジトリに無ければ `exit 1`。改名されると `gh pr list --label` が永久に 0 件を返す。
3. **入力の異常**: `stale_hours` は 0〜168 の整数に限定する。桁数を縛らないと `$(( S * 3600 ))` が 64bit を回り込んで負値になり、全件 skip で静かに緑になる。

### D5. 自分自身を編集する PR では DRY_RUN で走らせる

`workflow_dispatch` は既定ブランチに存在しない workflow を起動できない(`gh workflow run --ref <branch>` は HTTP 404)。マージ前に走らせる手段は `pull_request` トリガーしかない。`audit.yml` が同じ理由で自分自身を PR で走らせているのに倣う。

paths には watchdog 本体だけでなく、**D4-1 が監視している `fetch-news.yml` と `recheck-nikkyo-membership.yml` も含める**。含めないと、ラベルの改名が PR 段階で無検知のまま main に載り、次の cron まで気づけない。

PR 実行では Issue を作らない。ただし open な bot PR が 0 件だと検出ロジックが 1 行も走らないまま緑になるため、**合成 PR を 1 件注入してループ本体を必ず通す**。

### D6. 全 job が `timeout-minutes` を宣言する

| workflow | 値 | 根拠 |
| --- | ---: | --- |
| `checks` / `audit` / `dependabot-auto-merge` | 10 | 実測最大 0.8 / 0.2 / 0.1 分 |
| `cf-purge` | 20 | 内部で最大 10 分ポーリング(`seq 1 40` × `sleep 15`)＋ tag 解決失敗時の固定 3 分待ち。その上限の約 2 倍 |
| `e2e` / `vrt` | 30 | 律速はテストではなく Playwright / apt のインストール |
| `link-check` | 30 | 実測最大 15.2 分(外部サイトのレイテンシに依存) |

**`e2e` の値を成功実行の最大(9.4 分)から決めない。** その 9.4 分自体が apt 停滞によるもので、内訳は `install-deps` 8.6 分(通常 0.25 分)・テスト本体 0.2 分だった。2026-05 には install ステップだけで 16.15 分以上止まった実績がある。`vrt` は Playwright を毎回 uncached で入れ、ビルドを 2 回回すので同じ扱いにする。

## 影響と運用

- 滞留は通常 6〜8 時間、最悪 14 時間程度で Issue になる。Issue には success / skipped でない check 名と run URL が載るので、インフラ起因(`gh run rerun --failed` で足りる)かコード起因かをその場で判断できる。
- ハングの代償は 6 時間から 10〜30 分になる(12〜36 倍の短縮)。
- ラベル配線に人が触ると watchdog が赤くなる。**これは仕様**で、ラベルは D1 のとおり唯一の識別子なので、変更は人が見て `BOT_LABELS` を追随させる必要がある。

## 残余リスク(本 ADR では塞がない)

- **watchdog 自身が止まったことを検知する装置が無い。** cron が停止しても、workflow が disable されても、誰も気づかない。監視装置を監視する装置を足すかは、本装置の運用実績を見てから判断する。
- **bot が PR を「作らずに」失敗する経路は対象外。** `fetch-news.yml` は新着が無いとき `exit 0` するので、全フィードが壊れても緑・PR 無し・watchdog も無反応になる。ADR 0020 の health-check とも守備範囲が違う。塞ぐなら別 ADR。

## 撤回 / 再検討の条件

- bot PR の正常マージ時間が 2 時間に近づく(＝閾値のマージンが失われる)
- 誤検知が続く。特にラベル配線を触っていないのに D4-1 が落ちる場合は、抽出方法が実体に追随できていない
- GitHub が PR の停滞を標準機能で通知するようになる

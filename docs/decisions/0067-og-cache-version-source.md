# 0067. 動的 OG のキャッシュバスティングを単一の版数定数で行う

- 状態: 採用(0034 の動的 OG `?v=` 版元を上書き)
- 日付: 2026-08-22
- 関連 PR: `feat/og-cache-version-constant`
- 関連 ADR: [`ADR 0031`](0031-og-image-dynamic-with-bundled-font.md)(ダイジェスト個別ページの動的 OG) / [`ADR 0032`](0032-static-default-og-image.md)(静的 default OG) / [`ADR 0034`](0034-og-cache-refresh-policy.md)(OG キャッシュ更新ポリシー)
- 関連: [`docs/digest-workflow.md`](../digest-workflow.md)「執筆上の約束（要点）」の `title` 箇条

## 背景

ADR 0034 は動的 OG(`/og/digest/<slug>.png`)のキャッシュバスティングに frontmatter の `publishedAt` を `?v=` として流用すると決めた。**この決定は 3 か月半のあいだ実装されず、実装できないことが判明した。**

### 1. 実装 PR が存在しない

ADR 0034 §3 は「本 ADR を採択する PR ではコード変更を行わない、実装は別 PR」と書き、実装 PR の 4 ステップまで示した。採択は 2026-05-05。**本 ADR を起こす時点(2026-08-22)まで、その PR は起こされていなかった** — `ogVersion` / `OG_DEFAULT_VERSION` はリポジトリに存在せず、ビルド出力の `og:image` にはクエリが 1 件も付いていなかった。

本 ADR は D4 のとおり実装を同梱するので、この状態はマージ時点で解消する。

### 2. `publishedAt` は既に 3 役を担っていて、4 役目が載らない

`publishedAt` は digest 一覧とトップの最新号ブロックの並び順、ページ上の「公開日」表示、RSS の `pubDate` を兼ねている。ADR 0034 はこれに「OG キャッシュの更新日」を重ねた。

PR #553 で過去 16 号の title を新書式へ書き換えたとき、この重ね方が成立しないことが実測で確定した。ADR 0034 の運用ワークフローどおり 16 号の `publishedAt` を編集日時に書き換えると、**一覧の並びが今日順にリセットされ、RSS の `pubDate` が 16 件まとめて書き換わる**。そのため `publishedAt` は据え置き、`?v=` の更新は行わなかった。

(RSS の `guid` は `isPermaLink="true"` の URL なので、guid で重複排除するリーダーでは「新着 16 件」にはならない。壊れるのは並び順と日付表示で、既読の扱いはリーダー依存になる。)

ADR 0034 が選択肢 A の「欠点」に書いた「`publishedAt` を編集日時に書き換える運用ルールを徹底する必要がある」は、徹底の問題ではなく、**徹底すると読者向けの表示が壊れる**という構造の問題だった。

### 3. ADR 0034 自身が「別 ADR」と書いた条件が発火している

ADR 0034 の判断フレーム表は `src/lib/og-image.ts` のレイアウト変更を **「全 digest で必要」**に分類し、この場合は別 ADR を起こすか全 digest の `publishedAt` を一括更新する必要があり、いずれも同 ADR のスコープ外だと書いた。PR #553 はまさにそのレイアウト変更(title を 2 行に分割)であり、どちらの経路も取られていない。

同 ADR §撤回・再検討の条件の 3 つ目 —「digest 修正運用が頻発し、`publishedAt` を『初公開日時』と『OG キャッシュ更新日』の二重で扱うことに混乱が生じた場合、選択肢 B へ切替」— も発火している。頻発の側も実測で満たしている: 創刊号 `2026-04-25.md` は公開後に 8 本の PR で編集されている(#165 #169 #334 #335 #336 #415 #448 #553)。

### 4. ファミリーの実態は「揃っている」状態ではない

ADR 0034 は「姉妹 3 リポジトリ(portfolio / edu-evidence / edu-watch)で OG キャッシュ更新ポリシーを揃える」と書いたが、実装があるのは edu-evidence だけである(各リポジトリのビルド出力の `og:image` を実測)。

| リポジトリ | `?v=` の実装 | 動的 OG の版元 |
|---|---|---|
| edu-evidence | あり | `lastVerified`(戦略ページの frontmatter) |
| edu-watch(本リポ) | 本 ADR で導入 | `OG_DIGEST_VERSION`(D1) |
| ISAGAWA HAYATO Portfolio(起点 ADR 0003) | なし | — |
| edu-law | なし(ADR 0034 のスコープ外) | — |
| okinawa-in-data | なし(同上) | — |

edu-evidence が使っている `lastVerified` は **ADR 0034 が「過剰投資」として却下した選択肢 B の形**(専用フィールド)である。戦略ページは「いつ内容を検証したか」を読者に示す必要があるためこのフィールドを元から持っており、OG の版数と自然に噛み合う。digest にはこれに当たるフィールドが無い。

## 検討した選択肢

### A) 単一の版数定数(採用)

全 digest が 1 つの値を共有し、OG の見た目が変わる変更をしたらその値を上げる。

- 利点: 号ごとの記入・スキーマ変更・frontmatter 追加が不要。「いつ上げるか」の判断が 1 か所に集まる
- 欠点: 1 号だけ直しても全号の URL が変わる

### B) digest スキーマに専用フィールドを足す(ADR 0034 の選択肢 B)

edu-evidence の `lastVerified` に相当するフィールドを digest に新設する。

- 利点: 号ごとの粒度が得られる
- 欠点: 得られる粒度の実益は「SNS が再取得する枚数」だけで、正しさは A と変わらない。一方で 17 号ぶんの初期値記入と、号ごとの「上げるかどうか」の判断が恒久的に増える。digest には `lastVerified` のように**読者向けの意味を持つ既存フィールド**が無いので、OG のためだけのフィールドになる

### C) `publishedAt` の流用を続ける(ADR 0034 の決定)

背景 2 のとおり、書き換えると一覧の並び・公開日表示・RSS の `pubDate` が壊れる。実装しても運用できない。

## 決定

**選択肢 A を採用。**

### D1. 動的 OG の `?v=` は frontmatter ではなく単一定数から取る

`src/data/og-version.ts` に `OG_DIGEST_VERSION` を置き、全 digest がこの 1 つの値を共有する。OG 画像の見た目が変わる変更をしたら、この定数を変更日(`YYYYMMDD`)に更新する。

対象となる変更は 2 種類ある。

- `src/lib/og-image.ts` / `src/pages/og/digest/[slug].png.ts` のレイアウト変更(全号に効く)
- 個別号の `title` / `topics` / `weekStart` / `weekEnd` の編集(その号だけ効く)

後者でも全号の URL が変わる。**これは受け入れる** — 変わるのは SNS が再取得する画像の枚数だけで、配信されるのは同じ静的 PNG である。取りこぼす側に倒すと、X には公式のリフェッチ手段が無いため回復手段が残らない。

**新規号の公開では上げない。** URL 自体が新規なので、busting する対象のキャッシュが存在しない。

**付け忘れは型で止める。** `Layout.astro` の `Props` を判別可能ユニオンにしてあり、`ogImagePath` と `ogVersion` の片方だけを渡すと `astro check`(CI の required check「Type and text checks」)が落ちる。「取りこぼしが無い」ことを、呼び出し元がいま 1 つしかないという事実に依存させない。

### D2. 静的 default OG は ADR 0034 の決定のまま

`OG_DEFAULT_VERSION` をブランド改修時に手動更新する。ADR 0034 §2 と「ブランド改修するとき」の運用ワークフローは、そのまま有効。同じファイルに置き、本 ADR の PR でまとめて実装する。

### D3. `publishedAt` は OG と無関係になる

公開済みの号の title を後から直しても `publishedAt` は触らない。ADR 0034 の判断フレーム表(データ行 7)と、digest に関する運用ワークフロー 4 種(新規公開 / 修正・視覚差分あり / 修正・視覚差分なし / 動的 OG レイアウト全体改修)は、次の 1 行に置き換わる。

> **OG 画像の見た目が変わる変更をしたら、`OG_DIGEST_VERSION` を変更日に上げる。**

### D4. 実装は本 ADR と同じ PR で行う

ADR 0034 §3 は実装を別 PR に分離し、その PR が 3 か月半立たなかった。同じ分離は繰り返さない。実装は配線 3 ファイル(+31 / -4 行)と changelog 1 行で、レビュー粒度を分ける利得より、決定と実体が食い違う期間を作らないことを優先する。

## 帰結

- `OG_DIGEST_VERSION` は新規の値なので、**このデプロイで 17 号すべての OG URL が新しくなる**。過去にシェアされた digest の URL は、SNS 側の再取得のタイミングで PR #553 の 2 行 title のカードに入れ替わる
- 静的 default OG も同時にクエリ付きになる。トップ・カテゴリ・媒体・アーカイブ・about など、digest 以外のすべてのページが対象
- ADR 0034 は動的 OG の版元についてのみ本 ADR に上書きされる。共通フレーム(クエリで別 URL 化 + Debugger 併用)と SNS 別 runbook への参照、静的 default OG の扱いは 0034 のまま有効
- ファミリーは揃わないままになる。edu-evidence は `lastVerified` 由来を維持し、portfolio は未実装のまま。揃える判断は本 ADR のスコープ外

## トレードオフ / 既知のリスク

- **定数の上げ忘れは検知されない。** OG の見た目を変えたのに定数を据え置くと、SNS のカードは古いまま残る。CI で「`og-image.ts` が変わったのに定数が据え置き」を落とすことは可能だが、個別号の frontmatter 編集による見た目の変化は同じ手では検知できないため、片方だけ機械化しても「緑＝更新済み」と読める状態を作ってしまう。ここは運用で担保する
- **Cloudflare のエッジキャッシュはクエリをキーに含まない**(実測: クエリ付きで初回取得して MISS を出した直後、クエリ無しの要求が同じ ETag で HIT する)。つまり `?v=` はエッジのキャッシュを分けない。**それでも機構が成立するのは、SNS のクローラが URL 文字列単位で画像をキャッシュするため**で、狙っているのはそちら側である。ADR 0034 の撤回条件 2 が言う「クエリを付けた際の CDN キャッシュ挙動の不具合」には当たらない(同じ実体が返るだけで、壊れてはいない)
- 号ごとの更新を将来必要とした場合、選択肢 B への移行時に 17 号ぶんの初期値を決める作業が発生する

## 撤回 / 再検討の条件

- 特定の号だけ OG を作り直して SNS で再告知する運用が定着し、全号ぶんの再取得が実害になった場合、選択肢 B(専用フィールド)へ切り替える
- X が公式の Card Validator 相当を再提供した場合、ADR 0034 が引く portfolio ADR 0003 とともに、クエリ方式そのものの要否を再検討する
- 定数の上げ忘れが実際に起きた場合、機械的な検知(片手落ちであっても)を入れるかを再検討する

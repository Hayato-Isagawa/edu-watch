# 0087. CI は共有せずコピーのまま、ファミリーの workflow のずれを自動で見つける

- 状態: 採用(ADR 0086 の〈撤回 / 再検討の条件の点検の場〉を上書き)
- 日付: 2026-11-20
- 関連 PR: `docs/adr-0087-ci-drift-detection`(本 ADR 起票)
- 関連 issue: #1041(CI の共有の検討) / #1043(ずれの検出の実装)
- 関連 ADR: [ADR 0086](0086-reevaluate-separate-repositories.md)

## 背景

ADR 0086 は別リポジトリとコピー持ち込みを続け、CI の共有(reusable workflow・composite action など)は #1041 で
別に検討するとした。2026-11-20 に、ファミリーの 5 リポ(公開 4・非公開 1)の `.github/workflows/` を測った。

### 重なりの度合い(2026-11-20 時点。コメントと空行を除いて比べた)

- 2 リポ以上に同じ名前である workflow は 11 種類。そのうち `audit.yml`・`zizmor.yml` は 5 リポで同一、
  `cf-purge.yml`(3 リポ)の差は Worker 名の 1 行だけ。`ci-summary.yml` の差も、各リポの PR 検査の workflow 名の列挙など、
  設計上の差に限られる
- この 4 種類は、2026-05 以降の変更のほとんどが、同じ変更を各リポに入れたものだった
- `link-check.yml`・`vrt.yml`・`e2e.yml`・PR 検査系・`dependabot-auto-merge.yml`(3 系統に分かれている)は、
  リポ固有の変更が多い
- `stale-check.yml`(2 リポ)は名前だけが同じで、周期も処理も別の workflow

### 取り残し

- 公開リポで、誰でも ci-summary の通知を止められた穴の修正は、edu-watch(2026-10-23)から edu-evidence(2026-11-17)まで
  25 日遅れた
- 2026-11-20 の時点で、`link-check.yml` の修正 4 件が一部のリポに届いていない: issues: write を持つ job が main の
  npm キャッシュを読む(3 リポで未対応)、同じ job が lychee のキャッシュを読む(4 リポで未対応)、lychee の手順に
  job より短い時間制限を置く(4 リポで未対応)、`failIfEmpty: true` を明示する(1 リポで未対応)

### 共有するときの制約(GitHub の文書で確かめたもの)

- 公開リポに置いた reusable workflow は、非公開のリポからも呼べる
- reusable workflow を呼ぶ job には `timeout-minutes` を書けない(呼べるキーが限られる)
- 呼ばれた workflow の `GITHUB_TOKEN` の権限は、呼び出し側より上げられない。シークレットは自動では渡らない
- 呼び出した job の check-run の名前は「呼び出し側の job / 呼ばれる側の job」の形になる(公式の記述は無く、実例で確かめた)
- 各リポのテストは、`ci-summary.yml` と `zizmor.yml` の全体を写しで固定し、`ci-summary`・`link-check`・`cf-purge` などの
  `run:` を取り出して実行している。本体を共有リポへ移すと、これらは対象を失う

## 検討した選択肢

- **A) コピーのまま、ずれを自動で見つける** — テスト・required check・check-run の名前は変わらない。上の取り残し 4 件は、
  設計上の差を許可しておけば拾える種類だった。同じ修正を各リポに入れる手間は残る
- **B) A に加えて、コメントを除いた差が 0 の `audit.yml`・`zizmor.yml` を共有する** — この 2 種類は修正が 1 回で済む。共有用の公開リポを作り、
  `zizmor.yml` の全体を固定するテストを作り直す。共有リポの更新が Dependabot の自動マージで全リポに入る経路ができる
- **C) 設計上の差の少ない 4 種類(B の 2 つと `ci-summary.yml`・`cf-purge.yml`)を共有する** — 取り残しが最も減る。
  `ci-summary.yml` は各リポで数十本のテストが本体を見ていて、作り直しが最も大きい。cf-purge のトークンは明示的に渡す
- **D) コピーを続けるだけ** — 取り残しは今と同じく、誰かが気づくまで残る

## 決定

A を採る。CI は共有しない。2 つ以上のリポにある workflow のずれを、自動で見つける仕組みを置く。

取り残しが起きたのは、リポごとの差が多く共有に向かない `link-check.yml` と、通知の判定がリポごとの差を持つ
`ci-summary.yml` だった。A はこの種類にも効き、B・C のようにテストや権限の経路を作り直さずに済む。

ずれの検出は、次の要件で別の PR で実装する(#1043)。

- 対象は、2 つ以上のリポに同じ名前である workflow。名前だけが同じで中身の別な workflow(`stale-check.yml` など)は、
  一覧を持って対象から外す
- コメントと空行を除いて比べ、workflow ごとに許可した設計上の差(Worker 名・PR 検査の workflow 名の列挙・
  link-check の除外先など)の外に出た差を、ずれとする
- ずれを見つけたら、人に届く形で知らせる(黙って消えない。link-check の通知と同じ考え方)
- 週 1 回以上回す
- 置き場所と、非公開のリポの読み方は、実装の issue で決める

上の 2026-11-20 時点の取り残し 4 件は、検出を待たずに各リポで直す。

## ADR 0086 の条件の点検(2026-11-20)

#1041 で行うとした ADR 0086 の撤回 / 再検討の条件の点検は、次のとおり。

- CI を共有すると決めたとき — 当たらない(本 ADR は共有しないと決めた)
- セキュリティの修正の PR をマージし、同じファイルを持つ姉妹リポで同じ題の PR が 7 日以内にマージされなかったとき —
  当たらない。採用(2026-11-20)以降にマージしたもので候補になるのは、okinawa-in-data の
  `ci(link-check): drop the lychee cache from the job with issues: write`(2026-11-20 02:07 UTC)だけで、
  他のリポにまだ同じ題の PR は無い。ただし、これは ADR 0086 の PR のマージ(同日 07:21 UTC)より前で、
  ADR 0086 が挙げたセキュリティの修正の 4 つの類型(GHSA・zizmor の指摘・`public/_headers`・第三者が workflow の動作を
  変えられる穴)のどれにも当たらない(zizmor の cache-poisoning の監査は、リリースの workflow を対象にしている)。
  4 つを例示と読んで数える場合は、同じ題の PR が 2026-11-27 までに他のリポで入らなければ当たる
- UI の同じ題の PR が 3 か月続くとき・公開範囲やデプロイの構成が変わったとき — 当たらない

ADR 0086 の条件の点検の場は、#1041 から #1043 に移す。ずれの検出を入れた後は、検出が出す知らせも点検の材料にする。

## 帰結

- テスト・required check・権限の経路は今のまま
- 同じ修正を各リポに入れる手間は残る(特に `audit.yml`・`zizmor.yml`・`ci-summary.yml`)
- 取り残しは、検出の周期(週 1 回以上)のうちに見つかるようになる。見つけた後に直すのは人の作業のまま
- 許可した設計上の差の一覧を、workflow を変えるたびに保つ手間が増える

## 撤回 / 再検討の条件

ADR 0086 の撤回 / 再検討の条件は、そのまま有効(本 ADR が上書きするのは点検の場だけ)。それに加えて、次のときに見直す。

- ずれの検出を入れた後に、ADR 0086 の条件の 2 つ目(セキュリティの修正の取り残し。定義と数え方は ADR 0086 による)に
  当たる例が出たとき
- ずれの検出を入れてから 3 か月のあいだに、許可した設計上の差の一覧だけを直す PR の数が、ずれの知らせを受けて
  workflow を直した PR の数を上回ったとき
- ファミリーの公開範囲や、リポの数が変わったとき

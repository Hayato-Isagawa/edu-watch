# 週次ダイジェスト 共同制作フロー

EduWatch の週次ダイジェスト（`src/content/digests/YYYY-MM-DD.md`）は、**編集者主導の共同制作**で作る。**論点・主張・本文は編集者が担い、Claude は事実調査と清書を担う。** Claude が論点や本文を先回りして書かない。

> **背景**: digest #5（2026-05-23 号）で Claude が単独で全文を執筆した結果、論点・本文が編集者の意図と乖離し、PR #183 を撤回・再構築した。その再発防止として本フローを定める。

## 役割分担

| 担当 | 内容 |
|------|------|
| **編集者** | 採用記事の確定／節構成・順序の決定／各節の**論点（本文を含む）の執筆**／PR レビュー・マージ |
| **Claude** | 候補の洗い出しと**事実の調査・提示**（一次ソースで裏取り）／編集者の論点・本文の**清書**／ファイル作成・PR 起票 |

## 手順

### 全体

1. **採用記事の確定**（編集者）。Claude は候補一覧と事実確認を補助する。
2. **節構成・順序の決定**（編集者）。複数記事を 1 セクションに束ねる判断もここで行う。

### 各セクションごとに繰り返す

1. **Claude: 事実を提示** — 中立・出典つき。数値・固有名詞は一次ソースで裏取りし、推測で書かない。裏取りは生記事テキスト（`curl`）と一次 PDF（`pdftotext`）の逐語照合で行い、WebFetch の要約には依存しない（要約は非決定的で内容が揺れるため）。
2. **編集者: 論点（本文を含む）を提示** — 編集判断・主張・本文ドラフトは編集者が書く。
3. **Claude: 清書して提示** — 編集者の論点・本文を digest 文体に整える。**論点の中身は変えない。** 行うのは次のみ。
   - 事実・数値・固有名詞の補強と、**記事化されていない補足資料**（統計・自治体ページ・報告書 PDF など）への inline link 付与。**記事カード（Referenced articles）で読めるニュースの出典（新聞記事・その一次ソース）は本文にリンクを置かない**
   - 関連する EduEvidence 戦略・コラム、過去 digest への横断リンク
   - 「私」を主語にしない観察フレーミングへの統一
   - 太字・体裁の調整
   - 清書の最後に [deslop-checklist.md](./deslop-checklist.md) を通し、定型的・機械的な言い回し（擬人化主語・二項対比の連打・まとめの定型 等）を除く。**論点と数値は対象外**
4. **編集者が確認** → 次の節へ。

### 最後

1. 全節の清書が編集者の確認を得たら、**文体レビューを独立に回す**。清書の文脈を持たないレビュアーに号の全文を通読させ、「執筆上の約束（要点）」・[deslop-checklist.md](./deslop-checklist.md)・直近数号と突き合わせて、**体裁の指摘だけ**を受け取る（論点の中身は対象外）。診断は採ってよいが、**提示された文案はそのまま使わない**。
2. 文体レビューを反映してから、**後段検証ゲート**（下記「後段検証ゲート（最終本文の逐語照合）」節）を回す。最終本文を一次資料と claim 単位で逐語照合し、GO（機微ティアは編集者 sign-off）を得るまで PR に進まない。**順序は固定**で、逆順にしない（文体レビューは文言を変えるため、その後に原典照合を置く）。
3. ゲート通過後、**Plan Mode** で対象ファイルと出典を宣言してから作成する。
4. `npm run check` / `npm run build` と生成 HTML の確認を通す。
5. 同 PR 内で `changelog.astro` にユーザー価値のある変更を 1 行追記する（本文の読者体験が変わる場合）。
6. **開発サーバーを立ち上げて表示を確認する**（下記「表示確認ゲート」節）。**編集者の目視 OK を得るまで PR に進まない。**
7. ブランチを切って PR を起票する。**マージは編集者が行う**（Claude は自動マージしない）。

## 後段検証ゲート（最終本文の逐語照合）

事実検証には**清書前（pre-draft）**と**清書後（post-draft）**の 2 つの関門がある。

- **pre-draft**: 各セクション手順 1 と `digest-fact-checker`（執筆前ゲート）。編集者が「こう書きたい」と示した主張を、本文を起こす前に一次資料で確認する。
- **post-draft**: 本節。**公開されるそのままの最終本文**を、一次資料と claim 単位で逐語照合する。

> **なぜ post-draft が要るか**: 2026-06-27 の W26 号で、`digest-fact-checker` の「生徒**ら**2人が死亡」（＝生徒とその他で計 2 人・内訳未確定）という pre-draft の表現が、清書の過程で「生徒2人」へ**過度に特定**された。実際は生徒 1 人＋船長 1 人で、死者の身元を誤った。pre-draft 検証は通っていたが、**清書で混入した誤りを最終本文で照合する関門が無かった**ため、公開直前に編集者が気づくまで残った（PR #330。教訓は memory `feedback_ambiguous_collective_count`）。ゲートの本質は「清書後の本文を、清書の経緯を信用せず原典から引き直す」ことにある。

### 何を・どう回すか

1. 対象は**最終本文（公開されるそのままの文）の全 claim**＝数値・固有名詞・日付・引用・死傷者・法令・金額。
2. `digest-fact-checker` を**後段（post-draft）モード**で回す。入力は清書済みの最終本文と原典のみ。清書の経緯や「編集者がこう言ったから」は根拠にしない。
3. **独立第 2 パス**を併走させる（`edu-adversarial-verifier` と同じ独立反証の原則）。最終本文を「正しいと仮定せず」、原典だけからゼロに引き直し、清書の言い回しとの食い違いを能動的に探す。研究の効果量・出典帰属を含む回（例: 文科省委託報告書の数値）は `edu-adversarial-verifier` 自体を併用する。
4. 判定が STOP / HOLD の間は **PR に進まない**。修正 → 再照合してから先へ進む。

### 書き換えた文は必ず原典に当て直す

清書のあとに文を書き換えた場合（**圧縮・言い換え・分割・結合を含む**）、その文は検証済み文字列の残存チェックでは検証できない。残存確認は「落としていないこと」の確認であって、「書き換えた先が正しいこと」の確認ではない。**書き換えた文は、その形のまま原典に当て直す**。書き換えが公開直前であっても省略しない。

> **なぜこの一手が要るか**: 2026-07-26 の W30 号で、清書を終えたあとの言い換えによって「デジタル寄りでした」という断定が入った。原典は「デジタルの割合が半分程度以上のものを望む回答が多く見られる教科も存在」と述べており、断定の根拠は無い。検証済み文字列の残存チェックは通っていたが、**言い換えた先の文を原典に当て直す手順が無かった**ため、公開後に発覚して訂正になった。同型の誤りが前週の W29 号（`2026-07-19.md`）にもあり、訂正は 2 号にまたがった（ADR 0064）。

### グラフ・図の数値は PDF を直読する

`pdftotext` は棒グラフ・円グラフの凡例と数値の対応を壊す。割合の読み取りが claim に含まれる場合は、抽出テキストではなく **PDF のページそのもの**を見る。

加えて、**グラフに数値が印字されていない場合、目測で読んだ割合は本文に書かない**。原典の見出し文・注記が言語で述べている範囲（「〜を望む回答の割合が多い」「〜教科も存在」など）にとどめる。目測は選択肢の区分を読み違えているかどうかの判断材料にはなるが、本文の根拠にはならない。

### 抽出表（過度特定・改変の機械的検出）

最終本文から機微・要検証の要素を 1 項目 1 行で抜き出し、**原典の語を要約せず一字一句コピー**して照合する。本文の言い換えではなく原典のコピーを並べることで、清書での詰め過ぎ・正規化・改変が表で可視化される。

| 本文の記述 | 原典の逐語（コピー） | 出典 URL | 一致 |
|---|---|---|---|
| （例）生徒2人が死亡 | 「生徒**ら**2人が…」／ 文科省 PDF「生徒が死亡」 | （各 URL） | ✗ 過度特定 |

### 機微事実ティア（最重要・load-bearing）

**死傷者（死者・負傷者の数／身元／年齢）・法令（成立・公布・施行・条項・罰則）・金額（予算・賠償・コスト）**は、誤れば訂正が要る最も機微な事実。通常の逐語照合に加え、次の 4 点を**すべて**満たすまで公開しない。

1. **2 つの独立した一次源で照合する**。単一報道・単一の二次まとめでは不可（例: 所管庁の一次 PDF ＋ 複数の独立報道、または当事者発表＋公的記録）。
2. **逐語**。原典の表現を一字一句で確認し、要約・正規化・概数化しない。
3. **人物単位の内訳照合**。「N 人」を集団のまま扱わず、一人ひとりの属性（生徒／船長／教員／年齢）に分解し、各人が一次で確認できるまで人数・身元を断定しない。
4. **編集者の sign-off**。機微ティアに該当する記述は、最終本文の該当文を編集者が個別に承認する。

### 「〜ら N 人」曖昧フラグ

「〜ら N 人」「〜など N 件」「関係者 N 名」のような**集合表現**（X とその他で計 N の含意）を最終本文・一次資料に見つけたら、内訳が一次で確定するまで次のいずれかにする。

- 「ら」「など」などの**曖昧さを保持する**（"生徒ら2人" を "生徒2人" に詰めない）。
- **人数・身元の断定を避ける**。

過度な特定（over-specification）は、根拠の無い特定を足す点で捏造と同じ訂正リスクを生む。

### 適用範囲

- post-draft の**逐語照合＋抽出表は毎回（全 digest）**実施する。軽量で、数値・固有名詞・日付の取り違えを広く拾う。
- **機微事実ティアの 4 点規律は、claim が死傷者・法令・金額に該当する回のみ**発火する。重い手順をリスクに比例させ、毎週の運用が形骸化しないようにする。
- ゲートを抜けた後に誤りが見つかった場合(公開後の訂正)は、[`ADR 0064`](decisions/0064-post-publication-correction-policy.md) に従う。訂正は changelog の 1 行で開示し、その 1 行の型と下限は同 ADR の D3 に定めてある。

## 表示確認ゲート（開発サーバーでの目視）

**毎号必ず実施する。編集者の目視 OK を得るまで PR を起票しない。**

> **なぜ要るか**: PR の diff は Markdown のソースしか見せない。**折り返しと行数は生成 HTML の grep でも PR でも分からない**（字面の重複だけは機械でも数えられる）。詳細ページは title → summary →「今週の論点」（heading。原則 3 本）が縦に並ぶので、同じ語がどれだけ目に入るかは描画しないと判断できない。2026-08-16 号は title と 2 本目の heading に `教員2,000人の意識調査` が **13 字完全一致**で並び、`教員2,000人の` は title / summary / heading の **3 スロット**に出ていた。グローバル規約「見た目・操作が変わる変更は commit / push 前にローカルで目視確認する」を digest にも適用する。

### いつ回すか

手順「最後」の step 6。**changelog を書いた後、push と PR の前。**

digest は [`sprint-4-design.md`](./sprint-4-design.md) §5.1 のとおり先にブランチを切って逐次コミットするため、本ゲートは**コミット済みの状態で回る**。グローバル規約の「commit 前」は digest では **push / PR 前**と読み替える。ここで直した分は追加コミットにする。

> **書き換えたら後段検証ゲートに戻る**: 本ゲートが直す対象（title / summary / heading）には検証済みの数値が載っている。**1 文でも書き換えたら「後段検証ゲート」の「書き換えた文は必ず原典に当て直す」に戻る。例外なし。** ADR 0064 を生んだのは、まさにこの「ゲートの後に触る」経路である。

### 手順

1. **Claude が `npm run dev`（port 4323）を起動し、停止まで管理する。** 編集者に起動を頼まない。
2. **Claude が 320 / 390 / 768 / 1280 px で掃引し、実測値を出す。** 道具は **chrome-devtools MCP の `emulate`**（例: `320x700x2,mobile,touch`）。グローバル規約が折り返しの実測に指定している道具で、320 px をそのまま取れる。**ウィンドウのリサイズは使わない** — ブラウザ側の下限に阻まれて指定した幅にならず、下限値は道具ごとに違う。**同一オリジンの iframe を固定幅にする代替も使わない** — スクロールバーの分だけ内側が狭くなり（320 指定で 305px）、UA・`pointer` / `hover` メディア特性も親のままになる。実測で h1 の行数が 1 行ずれた。測るのは次の 4 つ。
   - **横溢れ**: `document.documentElement.scrollWidth - clientWidth`
   - **ビューポート外へ出る要素**: `main` 配下で `rect.right > document.documentElement.clientWidth` **または** `rect.left < 0`。`position: fixed`・非表示・`aria-hidden`・オフキャンバス（`transform` で画面外に置いたメニュー）は除外する
   - **テキスト矩形の重なり**: `main` 配下の `p` / `li` / `h1`–`h3` / `a` の総当たり。**祖先・子孫のペアは必ず除外する** — `a` は `p`・`li` の子なので、除外しないと無傷のページで数十件出る。**ベースラインは 0 件**で、1 件でも出たら見る
   - **見出しの折り返し行数**: `main` 配下の `h1`–`h2` で `Range.selectNodeContents` → `getClientRects()` を取り、**矩形の `top` でユニーク化して数える**。`length` をそのまま使うと実際の行数より多く出る — 日本語は文節ごとに矩形が返り、見出しを複数要素に分けている分も上乗せされる（実測で 5 行の h1 が 7、3 行の h2 が 6 と出た）
3. **最低 4 URL を見る。** `/digest/<日付>/`（詳細）・`/`（トップの最新号カード）・`/digest/`（一覧カード）・`/changelog/`。**他号と比べられるのは `/digest/` だけ**で、詳細ページにもトップにも他号の title / heading は描画されない。詳細ページは絶対値で見る（h1 の行数・最終行の字数）。
4. **OG 画像は実レンダリングで見る。** `/og/digest/<日付>.png`（末尾スラッシュを付けると 404）。**OG は title を 2 段に分けて描く**（[`src/lib/og-image.ts`](../src/lib/og-image.ts)。上段が扱う内容の列挙で 44px、下段が週で 32px）。**行数は字数ではなく描画幅で決まる。** 下段は常に 1 行。上段が 3 行になるのは全角のみで 49〜50 字から（測り方で 1 字ぶれる）で、title 規約の 45〜65 字は上段 24〜44 字にあたる（週の側は「 — 〈年〉年〈月〉月第〈N〉週の論点」で 21 字固定）ため、この帯なら上段は 2 行を超えない。実データ 17 号の上段は 29〜39 字で全件 2 行。**ただしカタカナが多いと同じ字数でも幅を食うので、title を触ったら必ず再レンダリングする。**
5. **Claude は URL と着眼点を編集者に提示する。** 実測値だけ渡して「問題なし」で終えない。編集者が見るべき点（字面の重複・折り返し・カードの見え方）を名指しする。
6. Claude が dev サーバーを停止する。
7. **編集者の OK を得る。** PR の起票は手順「最後」の step 7 で行う。

### このゲートで見つからないもの

- ピクセル単位の視覚回帰は **VRT** の担当で、そちらが権威。ただし VRT は `paths` 限定起動で、**digest PR では走らない**。理由は 2 つあり、digest 本体の `src/content/**` が対象外なのに加えて、同 PR で必ず触る `src/pages/changelog.astro` が `!` で明示除外されている（`src/pages/**` 自体は対象）。**列挙の正典は [`.github/workflows/vrt.yml`](../.github/workflows/vrt.yml)** で、ここには写さない。
- **本ゲートに機械検査は無い。** CI では一切検出されず、抜けても静かに通る。人が見る前提の関門である。

## Claude がやってはいけないこと

- 論点・本文を先回りして書く（手順 2 は編集者の領域）。
- 清書時に編集者の論点の中身を変える・足す（手順 3 は事実補強と体裁のみ）。
- 全文を単独で執筆する。
- 編集者の確認を飛ばして次の節やファイル作成に進む。

## 執筆上の約束（要点）

- **文体**: digest 本文は敬体（です・ます調）で統一する。
- **結びの型を固定しない**（2026-07-26 号から）: 節の結びを「〜が問われます」「〜に委ねられています」「〜要ります」のような抽象名詞＋受動で締める形と、「A も、B も」の対句は、号をまたいで反復すると機械的に読める。実測では 2026-04〜05 月の 1〜2 回 / 号が 07-11 号・07-19 号では 5 回 / 号まで増えていた。結びは動詞で締めるか、判断や行為の主体を名指す（例: 「決めるのは各学校と教育委員会です」）。[deslop-checklist.md](./deslop-checklist.md) 項目 5・6 を節の結びに適用したもの。清書後に文末の分布を数え、同じ語尾が全文の 3 割を超えていたら直す（直近号の実測は 1〜2 割）。数えるのは `comment:` ブロックだけで、記事カードの要約原文は含めない。
- **heading を号内で同じ鋳型に揃えない**: 3 本の heading は詳細ページで縦に並んで表示されるため、構文が一致すると型が目立つ。左半分・右半分の作り方を節ごとに変える。
- **事実段落の必須要素と簡潔さ**: いつ／誰が／何を・どうした＋見出しの数値 1〜2 個に絞る。内訳・前回比・手続きの詳細・機関や通知の正式名称は本文に詰め込まず、リンク先に委ねる（読者は必要なら出典に飛ぶ）。論点段落が参照する数値だけは事実側に残す。事実段落は 1〜2 文を目安に、最初の清書から簡潔に書く。出典はセクションの記事カード（Referenced articles）に委ね、本文中に出典リンクは置かない。記事化されていない補足資料のみ本文に inline link を付ける。
- **セクション統合**: 同テーマ／論点交差／週内同時性／編集者軸の意義の 4 軸のうち 2 軸以上で統合を検討。1 セクション最大 3 記事。
- **段落数の目安**: 単独 1 記事 = 3-4／統合 2 記事 = 4-5／統合 3 記事 = 5-6／digest 全体 = 12-18。上限は原則超えない。
- **heading**: 「論点 — 対象」のダッシュ区切り（`—` U+2014）、25-45 文字目安。断定指示（「〜すべき」）や一方的批判は避け、観察フレーミング（「残る／移る／見えてくる」）や問いかけで立てる。
- **一次資料の教訓・提言は同一項目の反対条件も見る**: 報告書の「教訓」「勧告」「提言」から 1 文を引くときは、同じ項目に併記された逆向きの留保（「ただし〜しすぎると」型）も原典で確認する。片側だけを引いても不正確にはならないが、節全体の方向づけが原典より強く出ることがある（実例: 2026-07-26 号 第2節の OECD（2020）引用）。
- **title**（2026-08-16 号から）: 「**扱う内容の列挙 — 〈年〉年〈月〉月第〈N〉週の論点**」。ダッシュは `—`（U+2014）1 本で、全長 45〜65 字目安。列挙は原則 3 件を `・` で並べる（節が 3 本の号は節と同数になる）。**節が 4 本以上の号は代表 3 件に絞る** — 全部並べると 45〜65 字に収まらない。落とした節は詳細ページの「今週の論点」に heading として残る。**号全体を束ねる総括句は置かない。**
  - **列挙は主体名だけで済ませない**。何についてのことかが分かる語を必ず含める。「生命保険会社の調査」は主体しか言っておらず何の調査か分からないので不可、「教員2,000人の意識調査」は可。**主体名を書くこと自体は禁じていない** — 「東大の生成AI講座」のように主体＋主題なら可。読者は一覧カードでこの 1 行だけを見て号を選ぶ。
  - **週番号は `weekEnd` が属する月で決める**。`publishedAt`（＝ファイル名の日付）でも `weekStart` でもない。月をまたぐ週は `weekEnd` 側の月に属する（例: 2026-07-04 号は `weekStart 2026-06-27` / `weekEnd 2026-07-03` なので「2026 年 **7** 月第 1 週」、2026-08-01 号は `weekEnd 2026-07-31` なので「2026 年 **7** 月第 5 週」）。第 N 週は、その月に入って最初の号を第 1 週とし、以降 1 ずつ増やす。
    - **公開済みで 2 号がこの規則から外れている**: 2026-05-02 号は `weekEnd 2026-05-01` で 5 月に入っているが「4 月第 5 週」。2026-04-25 号は 4 月に帰属する最初の号だが「第 4 週」で、創刊号だけカレンダー由来の番号から始めている。いずれも据え置く。
  - **なぜ総括を置かないか**: ① **どの一次資料にも無い編集上の主張が title に入る**。無関係な複数記事を 1 句で束ねるには、原典にない共通項を編集側で作ることになる。title は meta description / OG / RSS / 一覧カードで本文から切り離されて単独流通するため、帰属のない主張だけが露出する。後段検証ゲート（上記）が heading と summary の無帰属断定を止めているのと同じ理由で、title も対象にする。② **実測で反復していた**。旧書式で出していた 2026-04-25 〜 08-09 の **16 号のうち 7 号**が「決めた側 vs 届く現場」の同じ構図だった（この 16 号は後に新書式へ統一したので、**以下に引く title は当時のもの**。frontmatter からは消えたが、`/changelog/` の公開時エントリには残っている）。判定基準は「二項の一方が決定・発表の主体、他方が受容・実施の主体で、その落差を述べる形」。該当は 05-11「組み直しの輪郭は出たが、現場に届く設計はこれから」／05-23「打ち出された方向と、受け止め・振り返る側に残る問い」／05-30「方向は示されても、担い手と実効性が問われる」／07-04「制度を現場にどう根づかせるか」／07-11「掲げた方針に、担う中身は伴うか」／07-26「枠は国が、判断は現場に」／08-09「決まったことと、実際に行き渡ること」。**直近 5 号では 3 号**（07-11・07-26・08-09）。境界例（06-20・07-19・08-01）を含めれば 10 号になる。週ごとの記事が変わっても、3 本を束ねる抽象度まで上がると行き先が限られる。
  - **トレードオフ（承知のうえで採っている）**: 総括句は号の識別子として働いていた（changelog のリンクラベル、SNS カードの太字 1 行目）。新書式では列挙がその役を担うので、列挙の書き方が号の見分けやすさを決める。また新書式は**全号が同じ構造になる**。理由②が反復を問題にしているのと矛盾するように見えるが、揃うのは事実の並べ方であって、**帰属のない主張が毎週 1 つ生産されることはない**。定期刊行物の定型としての反復は受け入れる。
  - **過去号はすべて新書式**。2026-04-25 〜 08-09 の 16 号は、公開後に title を新書式へ書き換え、summary も本節の規約（号全体を束ねる総括文を置かない）に沿わせた。`publishedAt` は据え置いた。**ADR 0034 が定めた OG の `?v=` は未実装**で（`ogVersion` / `OG_DEFAULT_VERSION` はリポに存在せず、ビルド出力の `og:image` にもクエリが付かない）、上げてもキャッシュは busting されないため。据え置くことで公開日・一覧の並び・RSS は当時のまま保たれる。**列挙の件数の正例は 2026-06-06 号以降を見る** — それ以前の 6 号は節が 4〜6 本あり、列挙を 3 件に絞ってある。
  - **この規約に機械検査は無い**（`content.config.ts` は `min(1)` のみ、textlint は frontmatter を見ない、e2e / VRT も title を assert しない）。違反しても静かに通るので、レビューで人が見る。
  - 号を読む動機づけは `summary` が担う。論点そのものは sections の heading から詳細ページに「今週の論点」として自動表示される。
  - **字数の上限は OG ではなく一覧カードの縦の伸びで決めている。** OG は title を 2 段に分けて描くので、45〜65 字の帯なら上段は 2 行に収まる（実測は「表示確認ゲート」step 4）。効くのは一覧カードのほうで、320px では 4〜6 行になり、長くするほど 1 件が縦に伸びる。
  - 既に公開した号の title を後から変える場合、[`ADR 0034`](decisions/0034-og-cache-refresh-policy.md) は `publishedAt` を編集日時に書き換えると定めている（OG 画像のキャッシュ更新のため）。**ただし同 ADR §3 が「実装は別 PR」とした `?v=` の実装が存在しないので、現状この書き換えは no-op。** 実装が入るまでは、一覧の並びと公開日表示を守るために据え置く。未公開の号には適用しない。
- **summary**: 1〜2 文・100〜130 字目安のリード文。論点の列挙や無理な接続はしない（論点一覧は sections の heading から詳細ページに「今週の論点」として自動表示される）。meta description / OG / RSS / 一覧カードにそのまま使われるため、単独で読んで意味が通る文にする。**title の理由①と同じく、号全体を束ねる総括文は置かない**（「いずれも〜という動きです」型）。字数が足りないときは総括で埋めず、検証済みの事実（日付・人数・規模）を足す。**ただし title / summary は手順の最後に書くため、後段検証ゲートの後で触りやすい。足した事実は必ず post-draft ゲートに戻して原典に当て直す**（上記「書き換えた文は必ず原典に当て直す」と同じ規律。ADR 0064 を生んだのはこの穴）。
